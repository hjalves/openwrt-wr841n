# lanwatch: devices on the network

A small "Fing"-like service for the OpenWrt access point. It lists every device it can see on the LAN, with name, maker, IP, MAC address, and when each was first and last seen; devices first seen in the last 24 hours are highlighted. The page is **http://192.168.0.254/devices.html** (also linked from the landing page), and the data is available on ubus as `lanwatch`.

| | |
|---|---|
| Daemon | `lanwatch`, 28 KiB stripped |
| Links to | only libraries already on the router: `libubus`, `libubox`, `libiwinfo`, `libgcc_s`, uClibc |
| Vendor table | `/usr/share/lanwatch/oui.bin`, 29 KB |
| Page | `/www/devices.html`, about 12 KB |
| Flash used | about 28 KiB in total on install |
| RAM | about 840 KiB RSS, mostly shared libraries. The device table itself is at most 35 KB (256 × 140 bytes) |
| Installed | 2026-11-15, enabled at boot (`/etc/init.d/lanwatch`) |

## How it finds devices

This router is a bridge on the same network segment as every other device (the Huawei is the gateway). So it receives everyone's **broadcast and multicast** traffic, even from devices on the Huawei's own Wi-Fi. It never logs into the Huawei.

**Passive** (no traffic generated): a raw socket on `br-lan`, with a kernel packet filter so only these protocols reach the daemon:

| Protocol | What it gives |
|---|---|
| ARP | MAC and IP of anything that talks |
| DHCP | the requesting device's **hostname** (option 12) and vendor class (option 60, e.g. `android-dhcp-14`, `MSFT 5.0`); the server's ACK gives the assigned IP |
| mDNS | names a device announces for itself (`MacBook.local`), the `model=` of `_device-info` records, and reverse-lookup answers |
| SSDP / UPnP | the `SERVER:` header of TVs, consoles and media boxes |
| NetBIOS | replies to our name queries (Windows names) |
| Any IPv4 broadcast | that its sender exists, with its MAC and IP. The contents aren't read. Some devices ignore ARP and ping but keep broadcasting announcements; a Fine Offset weather station on this LAN broadcasts to UDP port 59387 every 2 seconds |

The socket asks the kernel for **all-multicast** reception (`PACKET_MR_ALLMULTI`). Without it, multicast for groups nobody on the router has joined (SSDP's 239.255.255.250, for example) is dropped before the socket sees it.

**Active, and gentle:**
- **ARP sweep:** every `sweep` seconds (default 300), one ARP request per address in the subnet, 20 ms apart. That's about 5 seconds for a /24, and it catches quiet devices. Larger subnets are limited to the /24 around the router.
- **Name queries:** after each sweep, for devices that answered but still have no name, it sends a NetBIOS node-status query and an mDNS reverse lookup sent straight to the device. Each device is asked at most once an hour.
- **Google Cast:** one multicast question for `_googlecast._tcp` per sweep. Cast devices use random host names but give their real name (`fn=`) and model (`md=`) in that service's TXT record.
- **UPnP:** one SSDP `M-SEARCH` for `upnp:rootdevice` per sweep. Many TVs, media boxes, consoles, printers, NAS boxes and routers only advertise when asked, and their answers carry no name. The name is in the standard UPnP **device description** at the answer's `LOCATION` URL. lanwatch fetches that description (an HTTP GET) and reads `<friendlyName>` (as the name) and `<modelName>` (as the details), for example `[TV] Samsung` / `UE32K5500`.
  - **Who gets fetched:** a `LOCATION` is used only if it points back to the device that sent it, at a LAN address. That's what stops a device directing the router to some other host.
  - **Limits:** one request at a time, a 3-second timeout, at most 16 KB read, and each device at most once a day.
  - **How replies are read:** they come from random source ports, so they're read on lanwatch's own UDP socket and matched to the device by IP. Unsolicited SSDP `NOTIFY` announcements are seen on the raw socket as before.

**This access point's own Wi-Fi clients** come from `libiwinfo` (the associated-station list), including their signal strength.

**Names** come from the best source available, in this order:
1. the router's own hostname (for itself);
2. DHCP;
3. Google Cast name;
4. UPnP `friendlyName`;
5. mDNS name;
6. mDNS reverse lookup;
7. NetBIOS;
8. random-identifier mDNS names such as `c9a655a3-…`, used only when nothing else exists.

**Details** come from: an mDNS model or Cast model, then the UPnP `modelName`, then the SSDP server header, then the DHCP vendor class, then "default gateway" for the router's default route.

**Vendor:** looked up in a built-in table of **10,551 MAC prefixes from 74 consumer and networking brands**, generated by `tools/mkoui.py` from nmap's IEEE-derived `nmap-mac-prefixes`. A device using a **private (randomised) MAC**, as current phones do per Wi-Fi network, has no maker in its address, so it's shown as "Private address".

**Online** means seen within the last two sweeps (plus a minute).

## Storage

The device list (first and last seen, names, details) is kept in RAM and saved to `state_file` (default `/srv/lanwatch/devices.dat` on flash):
- when a **new** device appears, at most once every 10 minutes;
- once a day if anything changed;
- on stop.

It's a few KB (140 bytes per device), rewritten whole and atomically, so flash wear is negligible. Keeping it on flash means a reboot doesn't make every device look new. Set `state_file` to `''` to keep it in RAM only.

The table holds up to **256 devices**. When full, the device seen longest ago is replaced, never the router's own entry. A flood of fake MAC addresses from a hostile machine on the LAN can push real devices out; they come back at the next sweep.

## ubus

| Method | Returns |
|---|---|
| `devices` | `{"devices": [...]}`, as listed below |
| `status` | interface, address, device / online / new counts, sweep interval and count, last sweep, frames seen, state file and last save |

Each device in `devices` has:
- **Always:** `mac`, `private_mac`, `first_seen`, `last_seen`, `online`, `new`, `seen_via`.
- **When known:** `ip`, `name` and `name_source`, `vendor`, `info` and `info_source`, `wifi_signal`.

An rpcd ACL allows **anonymous** read of these two methods, like the traffic data, so anyone on the LAN can see the list (which any LAN scanner app could find anyway). Nothing can be changed through it.

```sh
ubus call lanwatch devices
curl -s http://192.168.0.254/ubus -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"call","params":["00000000000000000000000000000000","lanwatch","devices",{}]}'
```

## Configuration

`/etc/config/lanwatch`:

| Option | Default | |
|---|---|---|
| `enabled` | `1` | |
| `interface` | `lan` | logical network; its bridge device is looked up from netifd |
| `wifi` | `wlan0` | this AP's Wi-Fi interface, for client signal (`''` = none) |
| `sweep` | `300` | seconds between ARP sweeps (60 or more) |
| `state_file` | `/srv/lanwatch/devices.dat` | `''` = RAM only |

## Limitations

- **Sleeping phones:** they answer ARP only now and then, so they may show without an IP or as offline until they wake.
- **Private MAC addresses:** a phone that resets its private address appears as a new device. Fing has the same problem.
- **Unnamed devices:** a device that never says its name (many IoT devices) stays "Unknown". The Huawei's DHCP list has every name, but needs its admin login, which this deliberately doesn't use.
- **Shared MACs:** devices that share a MAC address are merged into one entry; the IP shows whichever was seen last. This VM is an example: Wi-Fi bridging gives it its host Mac's MAC.
- **Silent devices:** a device that never sends anything (no ARP, no broadcast, no DHCP) can't be seen at all.
- **IPv4 only.** No port scanning.

## Build and install

```sh
make -C lanwatch                                                     # OpenWrt SDK in ../toolchain
python3 lanwatch/tools/mkoui.py /usr/share/nmap/nmap-mac-prefixes lanwatch/files/oui.bin   # regenerate the vendor table
```

Copy to the router with `router-ssh/copy`, then on the router:

```sh
cp lanwatch /usr/sbin/ && chmod 755 /usr/sbin/lanwatch
mkdir -p /usr/share/lanwatch && cp oui.bin /usr/share/lanwatch/
cp lanwatch.init /etc/init.d/lanwatch && chmod 755 /etc/init.d/lanwatch
cp lanwatch.config /etc/config/lanwatch
cp lanwatch.acl.json /usr/share/rpcd/acl.d/lanwatch.json
cp devices.html /www/
/etc/init.d/lanwatch enable && /etc/init.d/lanwatch start
/etc/init.d/rpcd restart        # loads the ACL; logs out open LuCI sessions
```

**Uninstall:**

```sh
/etc/init.d/lanwatch stop; /etc/init.d/lanwatch disable
rm -r /usr/sbin/lanwatch /usr/share/lanwatch /etc/init.d/lanwatch /etc/config/lanwatch \
      /usr/share/rpcd/acl.d/lanwatch.json /www/devices.html /srv/lanwatch
/etc/init.d/rpcd restart
```

## Verification performed (2026-11-15)

- **Test bed:** two isolated network namespaces on the VM, with the daemon built with AddressSanitizer and UBSan, and a Python simulated LAN sending raw frames from 7 fake devices. All checks passed, three runs in a row:
  - iPhone via DHCP hostname (beating its mDNS name);
  - ESP32 via mDNS reverse lookup;
  - Windows via NetBIOS;
  - LG TV via SSDP;
  - Pixel with a private MAC via DHCP and the server's ACK;
  - MacBook via mDNS with `model=`;
  - Google Cast via `fn=` / `md=`;
  - vendors, the router itself, and the namespace host found by the ARP sweep.
- **Bugs found and fixed while testing:**
  - multicast for unjoined groups was dropped, fixed with all-multicast;
  - the parsers rejected every sender for the first 2 seconds, until the interface address was read, fixed by reading it at startup;
  - a stray `?` from a carriage return in SSDP headers;
  - the router's own entry could be evicted from a full table.
- **Restart:** all 8 test devices came back with identical first-seen times, names, details, vendors and IPs.
- **Fuzzing:** 20,000 mutated ARP, DHCP, mDNS, SSDP and NetBIOS frames, a third of them from random source MACs. No crash and no sanitizer report; the table stopped at 256 and kept the router's entry.
- **UPnP addition** (same test bed, with two fake UPnP devices on their own `macvlan` interfaces):
  - **Name and model:** `[TV] Living &amp; Room` was decoded to `[TV] Living & Room`, with model `UE32K5500`.
  - **Cross-host trick:** a device answering with a `LOCATION` on another host was never fetched (0 requests).
  - **Hostile servers:** a 64 KB description, a server that never answers (3 s timeout) and broken XML were all handled without harm.
  - **Regression:** the earlier discovery and fuzz tests still pass with no sanitizer reports.
  - **Bugs fixed:**
    - the first version missed every search reply, because they come from random ports, as a capture of the real Samsung TV confirmed. They're now read on the UDP socket;
    - a 16 KB buffer was being stored in the binary, which grew to 44 KiB; it's now reserved at startup instead.
  - **On the LAN:** the Samsung TV became `[TV] Samsung` / `UE32K5500`, and the Huawei `Huawei router`.
- **Broadcast sightings** (same test bed):
  - a device that ignores ARP but broadcasts was listed with its IP;
  - a broadcaster from another subnet got no IP recorded;
  - multicast to unrelated groups was ignored;
  - discovery and fuzz tests still pass with no sanitizer reports.

  On the LAN, this found the weather station at `192.168.0.200` (`98:cd:ac:22:63:32`, Espressif). It answers neither ARP nor ping, so neither lanwatch's sweep nor `nmap` had found it. Its announcement also carries its name (`EasyWeather-WIFI6332`), but decoding that format would be specific to one maker's stations, so lanwatch doesn't.
- **On the LAN:** results compared with an `nmap -sn -PR -T3` ARP scan from the VM.
  - Every device `nmap` found was also found by lanwatch.
  - lanwatch also found a Wi-Fi client that never answered ARP, through this AP's station list.
  - Names came through mDNS reverse lookups (`Owen`, `claude-sandbox`, `asus-arch`) and Google Cast (`Chromecast`).
